What makes a professional prompt

Five characteristics that separate domain-expert prompting from generic AI use.

Business outcome first

Lead with what you're trying to achieve ("reduce support tickets" or "build a business case") before describing the task. The model orients around the goal, not just the mechanics.

Domain precision

Use exact product names, component codes, and system-specific vocabulary. Imprecise prompts return generic answers. Precise prompts return usable ones.

Output format specified

Define the structure you need before the model starts writing: table, bulleted list, Issue / Cause / Resolution. Format specification eliminates reformatting work.

Audience named

State who will read the output: "BTP administrator," "maintenance engineer," "executive sponsor." Tone, vocabulary, and assumed knowledge calibrate accordingly.

Scope boundaries drawn

Tell the model what NOT to do: "no numbered steps," "read-only scope," "no write-back to SAP." Boundaries prevent scope drift and off-brand output.

📊 Data strategy & analysis Driving ISQM ticket analysis and content investment decisions from data.
Pattern extraction and gap mapping
Analyze the ISQM closed case data for SAP APM, 2,753 tickets across 4 years. Identify the top recurring patterns and subpatterns by volume, map each to the existing support assistant tree nodes, and flag gaps where no documentation or content recommendation exists. Rank by ticket volume and categorize gap severity as High / Medium / Low.
Outcome framing Starts with the dataset scope, not the tool operation
Domain precision ISQM, APM, support assistant tree: exact system names
Output format Gap severity taxonomy specified (High / Medium / Low)
What it produced 17-pattern prioritization table that drove 12+ weeks of content work
Business case from a single metric
94.66% of SAP APM support cases were resolved without any KBA or FAQ, the resolution came entirely from the engineering or support team. Build a business case for documentation investment using this number. Calculate the cost-avoidance potential at 10%, 15%, and 20% deflection rates, and recommend the top 5 content areas to address first based on ticket volume data.
Outcome framing "Business case" stated as the deliverable, not "write a summary"
Precision Exact percentage (94.66%) drives specificity of the output
Scope Three deflection scenarios + top 5 priorities: bounded, not open-ended
What it produced Executive-ready framing for the TCO reduction workstream
🌳 Conversational design Designing support decision trees: the questions and content a customer sees before raising a ticket.

Gap node from scratch
The Event Mesh node in the SAP APM support assistant tree has no content. The dominant subpattern is Event Mesh webhook configuration failures, 116 out of 137 total Event Mesh tickets. Design the full node: functional area questions that distinguish configuration issues from connectivity issues, and 3–4 content recommendations that would have covered most of these tickets. Prioritize SAP Help Portal topics over KBAs where possible.
Problem framing "No content" stated explicitly: sets the scope (build, not improve)
Diagnostic goal Distinguishing config vs. connectivity issues = clinical design intent
Preference stated Help Portal over KBAs: reflects content governance preference

🤖 AI agent documentation Prompts that produce responsible AI content, scope sections, and trust-building documentation for Joule agents.
Responsible AI section
Write the AI Transparency and Responsible AI section for an SAP APM Joule agent. Cover: which LLM is used (SAP AI Core, Claude via AWS Bedrock), what the LLM does versus what is computed deterministically, an explicit statement that customer data is not used for model training, and guidance on how users can verify agent output in APM. Tone: informative and direct, not defensive or over-qualified. No numbered steps.
Technical precision LLM stack named correctly (AI Core + Bedrock + Claude)
Tone constraint "Not defensive or over-qualified": shapes the voice, not just the content
Scope boundary "No numbered steps": enforces prose format for agent docs
What it produced Trust-building section now used as reference across all APM agent topics
Scope and limitations section
Write the Scope and Limitations section for the APM Asset Performance Health Analysis Agent. The agent is read-only, runs in Joule, and retrieves health indicator data from SAP APM. Use "The agent..." framing throughout. Include a capabilities list (what it IS designed for) and a Limitations sub-section (what it CANNOT do). Limitations must be explicit: no write-back to SAP systems, no cross-system access, no predictive analysis, no real-time sensor data. Each limitation as a separate bullet.
Voice constraint "The agent..." framing enforced: key AI doc convention
Limitations pre-seeded Four specific limitations given: leaves no room for vague output
Structure defined Two-part section (capabilities + limitations) specified up front
What it produced Section that directly addresses the most common user trust questions
📝 Technical writing direction Prompts that drive troubleshooting content, structured entries, and doc-ready output for SAP Help Portal.
Troubleshooting entry from a ticket pattern
Write a troubleshooting entry for SAP APM component APM-AS-INT. Issue: S/4HANA to APM asset data synchronization fails after a BTP destination configuration change. Format: Issue (one sentence), Possible Causes (bulleted), Resolution (numbered steps, max 6). Audience: BTP administrator who has access to the BTP cockpit and APM admin settings. Do not repeat the issue in the cause list: causes should explain why it fails, not restate that it fails.
Component tag APM-AS-INT: enables filtering and routing in SAP support systems
Format enforced Three-part structure + max step count prevents bloat
Audience-specific BTP cockpit access assumed: calibrates technical depth
Quality constraint "Do not repeat the issue in the causes": a common doc antipattern caught up front
What's New entry from a feature brief
Write a What's New entry for the 2611 release of SAP APM. Feature: Equipment (E) and Functional Location (T) task list support in Implement Recommendations. The change allows users to select asset-specific task lists when creating work orders from recommendations. Audience: existing APM users upgrading from 2608. Length: 2–3 sentences. Lead with the user benefit, not the technical change. No marketing language.
Release anchor Version (2611) and delta version (2608) contextualize the change
User benefit first "Lead with benefit, not technical change": core release notes principle
Tone guardrail "No marketing language": keeps release notes factual
What it produced 2 What's New entries published in SAP Help Portal for the 2611 release

What this demonstrates

Why domain-expert prompting is a distinct and transferable skill.

Generic AI prompting produces generic output. What makes these prompts work is the domain knowledge behind them: knowing that 94.66% no-doc coverage is the right metric to anchor a business case; knowing that APM-AS-INT is the component tag for integration issues; knowing that agent docs need a human oversight disclaimer and that it must be mandatory, not optional; knowing the difference between a configuration question and a connectivity question in a support decision tree.

That knowledge can't be prompted in; it has to be held by the person writing the prompt. The prompts here are as much a demonstration of SAP APM domain expertise as they are of AI prompting technique.
