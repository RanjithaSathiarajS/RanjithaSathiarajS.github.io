When Documentation Fails AI:
A RAG Quality Audit

AI assistants don't fail because of bad models. They fail because of bad source content. This audit takes the top three SAP APM support ticket patterns (real customer questions, backed by 2,753 closed cases) and shows exactly where documentation breaks down in a Retrieval-Augmented Generation system, and what fixing it looks like.

How RAG Works: Where Docs Fit

Understanding the pipeline shows exactly where documentation quality determines AI output quality.

📄
Source docs

Help portal pages, KBAs, troubleshooting guides

✂️
Chunking

Docs split into small pieces. Quality here depends on doc structure.

🔢
Embedding

Each chunk → a meaning vector. Vague language = vague vectors.

❓
User question

Also converted to a vector

🔍
Retrieval

Closest chunks fetched. Wrong docs → wrong answer.

💬
LLM answer

Generated from retrieved chunks. Good in = good out.

The highlighted steps (chunking, embedding, retrieval) are where documentation quality determines whether the AI's answer is accurate or useless. A well-written doc doesn't just help a human reader. It produces retrievable chunks with precise meaning vectors that the system can match to real user questions.

The Audit

Three questions derived from the highest-volume SAP APM support ticket patterns. Each shows what a RAG system retrieves from typical documentation, and what it should retrieve instead.

Question 1 "Why isn't my S/4HANA equipment data showing up in SAP APM?" ISQM: Data Synchronization · 319 tickets
❌ Typical documentation
Source: Data Integration Overview (excerpt)

SAP APM integrates with SAP S/4HANA through the Data Replication Framework. Once the integration is configured, data flows automatically to the APM system. If issues occur, verify that the configuration steps were completed correctly.

For further assistance, contact your system administrator or refer to the configuration guide.

What RAG retrieves
The chunk retrieved mentions "Data Replication Framework" and "S/4HANA," a partial match. But it contains no specific error conditions, no actionable steps, and no terminology the user actually searched for ("not showing up", "missing", "sync failed"). The LLM generates a generic answer: "verify your configuration." The customer still opens a ticket.
Failure type: Assumed context + vague resolution language. The doc describes the happy path only. No error scenarios. "If issues occur, verify configuration" is not an answer; it's a redirect.
✅ RAG-ready documentation
Rewritten: Troubleshooting S/4HANA to APM Data Synchronization

Symptom: Technical objects (equipment or functional locations) created or updated in SAP S/4HANA are not appearing in SAP APM.

Likely causes:

1. The DRF outbound implementation for APM is not active in S/4HANA.
2. The technical object type is not included in the replication filter.
3. The APM BTP destination is misconfigured or unreachable.

Resolution: In S/4HANA, open transaction DRFOUT and verify that the APM outbound implementation is active and the object filter includes equipment (E) and functional location (T) types.

What RAG retrieves now
The chunk matches on "S/4HANA," "APM," "not appearing," "equipment," "functional locations," and "synchronization." The LLM generates a specific, actionable answer including the transaction code and exact filter to check. The customer self-serves.
What changed: Symptom stated explicitly. Causes enumerated. Resolution is step-specific with real system references (DRFOUT). Each sentence is independently retrievable and meaningful without context from surrounding sections.
Question 2 "How do I get an X-API-Key to connect to SAP APM?" ISQM: API Access · 296 tickets
❌ Typical documentation
Source: API Access Overview (excerpt)

SAP APM exposes REST APIs for external integrations. Authentication is handled via API keys, which can be obtained through the standard SAP BTP service key process.

See the SAP BTP documentation for information on creating service instances and service keys. The API key should be included in the request header.

What RAG retrieves
The chunk matches "API" and "API keys" but the retrieved content redirects to BTP documentation without explaining the APM-specific steps. "Standard SAP BTP service key process" means nothing to a developer who is APM-first, not BTP-first. The LLM produces a generic BTP answer, not an APM answer.
Failure type: Assumed prerequisite knowledge + cross-reference without context. The doc assumes the reader knows the BTP service key flow. A chunk that says "see the BTP docs" retrieves as a dead end.
✅ RAG-ready documentation
Rewritten: Getting an X-API-Key for SAP APM

To authenticate API calls to SAP APM, you need an X-API-Key. This key is generated from a service instance in SAP BTP.

Steps:
1. In the SAP BTP cockpit, navigate to your APM subaccount.
2. Go to Services → Instances and locate your SAP APM service instance.
3. Select the instance, then choose Create Service Key.
4. Copy the value of the x-api-key field from the generated JSON.
5. Pass this value as the X-API-Key header in all APM API requests.

What RAG retrieves now
The chunk matches "X-API-Key," "SAP APM," "API calls," and "authenticate." The steps are self-contained, with no external redirect needed. The LLM produces a step-by-step answer directly. 183 of 296 tickets asked exactly this question.
What changed: The outcome (get an X-API-Key) is in the heading. Steps are explicit and APM-specific, not delegated to another product's docs. The chunk works standalone, with no surrounding context required to understand it.
Question 3 "My SAP APM subscription on BTP failed. What do I do?" ISQM: Tenant Provisioning · 257 tickets
❌ Typical documentation
Source: Initial Setup Guide (excerpt)

To set up SAP APM, subscribe to the application in the SAP BTP cockpit. Ensure that all prerequisites are met before subscribing. After a successful subscription, the APM tile will appear in your BTP subaccount.

If the subscription fails, ensure your BTP account has the necessary entitlements. Contact your BTP administrator for further support.

What RAG retrieves
Matches "subscription" and "BTP" but the only resolution offered is "check entitlements" and "contact administrator," the same advice support agents give before escalating. The LLM mirrors this unhelpfully. Customer still opens a ticket.
Failure type: Error scenario without error differentiation. "Subscription fails" covers at least five distinct root causes. A single generic chunk can't answer all of them, and trying to match all five creates a diluted embedding that matches none well.
✅ RAG-ready documentation
Rewritten: Troubleshooting SAP APM BTP Subscription Failures

Error: APM subscription in BTP subaccount shows status "Failed" or does not complete.

Check 1: Missing entitlement: In BTP cockpit → Entitlements, confirm that SAP Asset Performance Management is listed and has available quota for your region.

Check 2: Wrong BTP region: APM is available in EU10, EU20, US10, and US20. Subscriptions attempted in unsupported regions fail silently. Verify your subaccount region matches an APM-supported region.

Check 3: Azure subaccount dependency: APM on EU10/EU20 requires an active Azure subaccount link. If this is missing, the subscription will fail after initiation.

What RAG retrieves now
Three separate retrievable chunks, one per failure type. Each matches a distinct user scenario ("failed status," "wrong region," "Azure subaccount"). The LLM can answer the specific variant the customer is experiencing, not just the general category.
What changed: One generic error scenario split into three specific, independent chunks. Each has its own symptom, cause, and fix. A customer asking about regions gets the region chunk. A customer asking about Azure gets the Azure chunk. Precision replaces generality.

What the Audit Found

Three documentation failure patterns: each one invisible to a human reader, fatal to a RAG system.

Failure pattern What it looks like Why RAG fails The fix
Context assumed "If issues occur, verify the configuration." Sounds fine to a reader who just read the setup steps. Retrieved alone, the chunk contains no diagnosis. The LLM has nothing specific to say. State the symptom explicitly. Write every troubleshooting chunk as if it's the only thing the reader sees.
Cross-reference dead end "See the BTP documentation for service key creation." Acceptable in a linear guide. RAG retrieves this chunk as the answer to "how do I get an API key," but the chunk is just a redirect. No answer lives here. Inline the critical steps. A chunk that only points elsewhere is a retrieval dead end.
Undifferentiated errors "If subscription fails, check entitlements." One sentence for five failure modes. The embedding is diluted: it partially matches many questions and precisely matches none. Retrieval quality drops. One chunk per error scenario. Atomic, specific, self-contained. Each error gets its own symptom, cause, and fix.

What This Means for AI Assistants

The three questions in this audit represent 872 real support tickets. That's 32% of all SAP APM cases analyzed: cases where customers could not self-serve, not because the AI was wrong, but because the source documentation wasn't written for retrieval.

The diagnosis is documentation, not the model

Engineers deploying AI assistants default to model tuning, prompt engineering, and retrieval parameter tweaking when answers are wrong. These help at the margins. The structural problem is upstream: content written for linear human reading produces low-quality chunks, imprecise embeddings, and irrelevant retrievals, regardless of which LLM processes them.

You cannot fine-tune your way out of a documentation gap. If the answer isn't in the source content in a retrievable form, no model can generate it reliably.

The role that fixes this

An AI Knowledge Quality Engineer audits the source content layer, not the model, not the retrieval parameters, but the documentation itself. They ask: does this content work when a RAG system chunks and retrieves it? Does each section stand alone? Are symptoms stated explicitly? Are error scenarios differentiated?

This audit is that practice applied to three real customer questions. The methodology scales to the entire SAP APM documentation set, and to any enterprise deploying AI on top of existing knowledge content.
