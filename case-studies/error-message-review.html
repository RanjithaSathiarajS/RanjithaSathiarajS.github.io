Error Messages SAP Writing Standards Technical Writing

Error Message Review:
SAP Asset Performance Management

A review of system error message strings in SAP APM against SAP enterprise writing standards, covering clarity, actionability, and user-centricity. This is an ongoing review; entries are added as new strings are identified.

30 Strings reviewed
22 Missing actionable instructions
4 Systemic patterns

Context

What was reviewed

System-level error message strings surfaced in the SAP APM UI, triggered when users attempt actions that cannot be completed due to data constraints or configuration requirements. These messages are the first (and often only) guidance a user receives when something goes wrong.

Review criteria

  • SAP enterprise writing standards (active voice, sentence case, articles)
  • Message structure: what failed + why + what to do next
  • Avoidance of passive constructions and vague causation
  • Differentiation between similar error conditions
  • No unexplained technical or legal constraints in user-facing text

Reviewed Strings

Each entry shows the original string, the issues found, and the recommended replacement.

Product Occurrence

PRODUCT_OCCURRENCE_HAS_ASSIGNED_PRODUCT_INDIVIDUALS
Original

Cannot remove the product occurrence because product individuals are assigned.

Revised

Cannot remove the product occurrence. Unassign all product individuals first, then try again.

  • "Are assigned" is passive and incomplete: assigned to what?
  • No actionable instruction: user has no path forward
  • Fix: split into what failed + what to do; use active voice
TECHNICAL_OBJECT_ASSIGN_NO_PRODUCT_OCCURRENCE
Original

Cannot assign the technical object because the system element has no product occurrence. Assign a product occurrence to proceed.

Revised

Cannot assign the technical object because this system element has no product occurrence. Assign a product occurrence to this system element, then try again.

  • Best-structured of the four: correct pattern: what failed + why + what to do
  • "The system element" → "this system element" (more specific)
  • "To proceed" → "then try again" (clearer, action-oriented)
PRODUCT_OCCURRENCE_ASPECT_TYPE_INVALID
Original

Cannot assign the product occurrence for this aspect type because of the system category restrictions.

Revised

Cannot assign the product occurrence to this aspect type due to system category restrictions. Check the system category configuration and try again.

  • "For this aspect type" → "to this aspect type" (correct preposition)
  • "Because of" → "due to" (more concise, standard in SAP messages)
  • No actionable instruction in original: added next step
PRODUCT_OCCURRENCE_NOT_ISO_CATEGORY
Original

Cannot assign the product occurrence for product aspect type because of the system category restrictions.

Revised

Cannot assign the product occurrence because it does not meet the category requirements for this product aspect type. Select a compatible product occurrence and try again.

  • Missing article: "for product aspect type" → "for this product aspect type"
  • Too similar to the previous string; users cannot distinguish between the two error conditions
  • The actual constraint (a specific category requirement) was not surfaced; revised message describes the requirement without referencing the underlying standard
  • No actionable instruction in original: added next step

Systemic Pattern

01

Error messages explain the problem but not the solution

10 of 17 strings describe what cannot be done but leave no path forward. SAP enterprise writing standard for error messages: what failed → why → what to do next. All three parts are required. "What to do" is the most important and the most consistently missing, especially in bulk-action and consolidation validations, where the constraint is clear but the resolution is not.

02

Missing articles before noun phrases

4 of 7 strings in the second batch were missing "a" or "the" before noun phrases ("Industrial system has no…", "Functional failure not found", "Cannot exclude or include functional failure…"). This is a recurring pattern in system-generated strings, likely because they originate as code comments or key names rather than copy written for the UI.

03

Status names in quotes

Across multiple status-related messages, status values appear in single or double quotes ("Released", 'Reopen'). SAP enterprise style does not quote status names. Quotes add visual noise and imply a label rather than a state value. Status names should appear unquoted: "in Released status", "change the status to Reopen".

04

Code identifiers leaking into user-facing messages

At least one string contained a raw camelCase identifier (ConsequenceAssessment) in place of the human-readable term (consequence assessment). This is a systemic risk in string files authored by developers: internal class or variable names get copied directly into message text. All user-facing strings need a copy review pass before release.
