Context

A new type of software required a new type of documentation, and someone to figure out what that actually means in practice.

The challenge

SAP APM began shipping AI-powered agents in Joule: autonomous assistants that retrieve data, analyze health conditions, and surface recommendations for maintenance engineers. These agents behave differently from standard software features. They use LLMs, produce advisory output, and interact with customer data in ways that require explicit transparency.

Standard SAP help topics follow a Context / Procedure / Results format built around what the user does. For AI agents, that model breaks: there are no user steps. The agent does the work. A documentation framework existed for this content type, but applying it to a real industrial product required decisions the framework couldn't make for you.

Where the real work is

A framework tells you which sections to include. It doesn't tell you what a maintenance engineer in a petrochemical plant actually needs to trust an AI assistant. It doesn't tell you how to write example prompts that reflect real investigation workflows, not demo scenarios. It doesn't tell you which responsible AI language is informative versus defensive, or how to explain an LLM to someone who just wants to know if their plant data is safe.

Those are judgment calls. That's where the writing happens. That's what this case study is about.

How AI Agent Docs Differ

Four structural shifts from standard technical documentation.

Agent voice, not user voice

Standard help topics describe what the user does: "Select the asset, then click Analyze." Agent docs describe what the agent does: "The agent retrieves health indicators from APM and identifies assets with degraded condition scores." The subject of every sentence shifts from user to system.

No procedure steps

Agents don't expose a step-by-step workflow. Interaction is conversational: the user types a natural language prompt and the agent responds. Documentation uses narrative prose and example prompts instead of numbered procedures.

Scope and limitations are first-class

In standard docs, limitations are a footnote. In agent docs, they're a primary section. Users need to know exactly what the agent cannot do (no write-back, no cross-system access, no predictive analysis) before they can responsibly rely on its output.

Trust infrastructure is required

Every agent doc includes: which LLM is used, what data is processed, whether customer data trains the model (it doesn't), how output can be verified, and a human oversight disclaimer. These sections don't exist in standard feature docs: they're net-new for AI.

The Judgment Calls

What applying an AI documentation framework to a real industrial product actually required.

1

Rewriting for agent voice, not user voice

Every sentence in standard SAP docs starts with what the user does. For agents, that inverts. "The agent retrieves health indicators from APM and identifies assets with degraded condition scores." Retraining your writing instinct to describe system behavior instead of user action sounds minor. In practice, it changes every sentence in every section.

2

Deciding what counts as a limitation

The framework says include a scope and limitations section. It doesn't say which limitations matter to a maintenance engineer. Through the process of writing these sections for APM agents, a pattern emerged: users care most about write-back (the agent can't change anything in SAP), cross-system access (it only sees APM data), and predictive capability (it reports what's happening now, not what will happen). Those three answer 90% of the trust questions before they're asked.

3

Writing responsible AI content that doesn't read like a legal disclaimer

The required content is clear: which LLM, training data policy, output verification, human oversight. The challenge is tone. Written defensively, it reads as a warning that makes users distrust the tool before they've tried it. Written plainly, it builds exactly the confidence the section is meant to provide. That line is a writing judgment, not a compliance one.

4

Making example prompts actually useful

Most AI product docs show prompts like "Summarize the asset health report." A maintenance engineer in an active plant doesn't think that way. They think: "Alert came in at 2am: what triggered it, which asset, is it still active?" Writing prompts that match real investigation workflows required understanding what the job actually looks like. That knowledge isn't in the framework.

Writing Example Prompts

A core section of every agent doc. The challenge: write prompts that are genuinely useful to a maintenance engineer, not generic AI demos.

The problem with generic prompts

Most AI documentation shows prompts like "Summarize the asset health report." These are illustrative but not actionable: they don't reflect how a real engineer investigates an actual problem in their plant.

Good example prompts are grouped by intent, written in first person, and reference real enterprise objects (asset IDs, functional locations, indicator types). They show what the agent is specifically capable of, not what a generic LLM can do.

How they're written

Example prompts are written by mapping user scenarios to natural language patterns, then drafting specific, intent-driven sentences. Each prompt group has a label ("Investigating a specific asset") followed by 2–4 variations that represent how different users in that scenario would phrase the same need.

Rule: Example prompts must be actual sentences a user would type, not descriptions of what to type.

Sample output: prompts written for the APM Health Analysis Agent

Investigating a specific asset

  • What is the current health status of pump P-1023 in plant DE01?
  • Show me the open health alerts for functional location FL-COMP-004.
  • Which indicators triggered the degraded condition score on compressor C-0087?

Analyzing trends across assets

  • Which assets in plant US10 have shown declining health scores over the last 30 days?
  • List the top 10 assets by number of open health alerts this quarter.
  • Are there any assets approaching a critical threshold that haven't been reviewed yet?

Diagnosing an alert condition

  • Alert #ALT-00492 was triggered last night. What caused it and is the asset still in a degraded state?
  • Explain the health indicators that contributed to the critical alert on turbine T-0051.
  • What does the vibration indicator trend look like for motor M-0113 over the past 14 days?

Supporting a decision

  • I'm deciding whether to schedule maintenance for heat exchanger HX-0022 this week. What does the health data show?
  • Summarize the health status of all assets assigned to maintenance planner MP-007 for this week's review.

Responsible AI Content in Practice

What the AI transparency and human oversight sections actually contain, and why each piece is necessary.

1

LLM disclosure

Names the model used (e.g., Claude via AWS Bedrock, served through SAP AI Core) and distinguishes what the LLM does from what is computed deterministically. This prevents users from assuming the entire agent response is AI-generated: some retrieval and filtering is rule-based.

2

Training data statement

An explicit statement that customer-specific data (asset records, alert history, indicator readings) is not used to train or fine-tune the underlying model. This is a hard requirement for enterprise customers with data governance policies. It must be stated plainly, not buried.

3

Output verification guidance

Instructions for how users can cross-check agent output against source data in APM. For advisory agents, this is critical: users need a path to verify before acting on a recommendation. Documentation that skips this step implicitly asks users to trust blindly.

4

Human oversight disclaimer

"The agent's output is advisory only. Decisions must be reviewed and confirmed by a qualified maintenance professional before any action is taken." This disclaimer is mandatory for all APM agents that produce recommendations. It protects both the user and SAP, and sets the right expectation for how the tool is meant to be used.

Outcome

What this work built, beyond the documents themselves.

Fluency in a new content discipline

Writing AI agent documentation for the first time in a production product is different from understanding the theory. The APM agents were the practice ground. The result is a working knowledge of what responsible AI content actually requires, not just the sections, but the reasoning behind every sentence.

A point of view on AI documentation

Enterprise AI documentation is still being invented. Most products ship agents with feature docs that describe buttons and menus, as if the AI doesn't change the contract between the product and the user. It does. Working through the APM agents built a clear perspective on what that contract requires, and why most current AI docs fall short of it.
