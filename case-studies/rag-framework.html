RAG Readiness Audit
Framework

A repeatable methodology for evaluating whether enterprise documentation is fit for AI retrieval. Produces a scored, prioritised audit report, identifying exactly which content fails in a RAG pipeline, why it fails, and what the fix looks like.

5 Scoring dimensions per content chunk
5 Phases, from question sourcing to final report
3 Named failure patterns with defined fixes
Scalable Runs on any documentation set, any product

Why This Exists

Companies deploying AI assistants optimise the model. The real problem is upstream.

The wrong place to look

When an enterprise AI assistant gives a wrong or incomplete answer, the default response is to tune retrieval parameters, adjust chunk size, or try a different embedding model. These interventions help at the margins. The structural problem they don't fix is content quality: documentation written for human readers that breaks apart when a RAG system chunks and retrieves it.

You cannot retrieve what was never written in a retrievable way. No model improvement substitutes for source content that is contextually complete, terminologically precise, and structured around distinct user intents.

The right place to intervene

The RAG Readiness Audit Framework evaluates documentation at the content layer, before the pipeline, not after. It answers three questions: Does each content chunk stand alone? Does it use the language users search with? Are failure scenarios separated so each one can be retrieved independently?

The output is an actionable, prioritised report, not a general recommendation to "improve docs," but a scored list of specific content items, their retrieval failure mode, and the exact rewrite needed. Engineers can act on it. Documentation teams can prioritise against it.

The 5-Phase Process

From question sourcing to final report: each phase has defined inputs and outputs.

1

Source audit questions

Derive real user questions from support ticket data (ISQM, Zendesk, ServiceNow), search query logs, or failed AI assistant interactions. Each question represents a real retrieval need. Prioritise by volume; the most common questions expose the highest-impact gaps.

In: Ticket data / search logs / AI session logs Out: Prioritised question list with volume weights
2

Map questions to source content

For each question, locate the documentation that should contain the answer. If no content exists, that is itself a finding (Coverage Gap). If content exists across multiple pages or sections, identify each candidate chunk separately.

In: Question list + documentation set Out: Question → content mapping; coverage gaps flagged
3

Score each content chunk

Apply the 5-dimension scoring rubric to each mapped chunk. Score each dimension 0–2. Identify the primary failure mode using the named pattern taxonomy. Total score out of 10 determines the retrieval band: Not Retrievable (0–4), Partial (5–7), or RAG-Ready (8–10).

In: Content chunks Out: Scored inventory with failure mode per chunk
4

Draft rewrites for failing content

For every chunk scoring below 5, produce a rewritten version that addresses the identified failure mode. The rewrite is scoped to retrieval quality, not a full content overhaul. Focus: make the chunk standalone, align its terminology to query language, and split mixed-intent content into atomic pieces.

In: Scored inventory (0–4 band) Out: Before/after pairs for each failing chunk
5

Deliver the audit report

Compile findings into a structured report: coverage summary, score distribution, failure pattern breakdown, prioritised rewrite recommendations, and projected retrieval improvement. The report is actionable by both documentation leads and AI engineering teams.

In: Scored inventory + rewrites Out: Audit report (executive summary + full findings)

The Scoring Rubric

Five dimensions. Each scored 0–2. Maximum score per chunk: 10.

Dimension 0 Fails 1 Partial 2 Passes
Standalone completeness Meaningless without surrounding context, references "the previous step," "as described above," or an unstated subject Mostly self-contained but assumes one piece of prior knowledge Fully understandable in isolation; no external context required
Query-term alignment Uses only internal product terminology or UI labels that users would not search with Mixes product terms with some task-oriented language Uses the words and phrases users actually type when asking about this problem
Error specificity Multiple distinct failure scenarios handled in one undifferentiated chunk Some scenario differentiation but at least two failure modes share a chunk One chunk per failure scenario; each symptom, cause, and fix is atomic
Actionability Describes the situation or redirects to another resource without providing resolution steps Provides partial resolution: what to check but not what to do with the result Specifies exactly what to do, including system location, transaction code, or field name
Entity precision Vague references: "the system," "the relevant setting," "the configuration" Names the product but not the specific path, field, or object Names the exact UI element, transaction code, API parameter, or configuration path
0–4 Not Retrievable Rewrite required before this content can contribute to accurate AI responses.
5–7 Partially Retrievable Content will sometimes retrieve correctly but fails on specific query variants. Improvement recommended.
8–10 RAG-Ready Chunk is structurally fit for retrieval. Passes all five dimensions at an acceptable level.

Named Failure Patterns

Five recurring documentation failure modes, each with a defined cause and a standard fix. Using a shared taxonomy makes audit findings consistent across reviewers and actionable for writers.

Pattern 01
Assumed Context

The chunk relies on information from a preceding section that won't be retrieved alongside it. Pronouns without referents, "as described above," or steps that reference an unstated prerequisite.

Restate the subject and prerequisite in every chunk that needs it.
Pattern 02
Cross-Reference Dead End

The chunk's only answer is a pointer to another document or section. When retrieved alone, it contains no actionable information, just a redirect that the RAG system cannot follow.

Inline the essential steps. A chunk that only points elsewhere is a retrieval dead end.
Pattern 03
Undifferentiated Errors

Multiple failure scenarios share a single chunk. The embedding is diluted; it partially matches many user queries and precisely matches none. Retrieval quality drops across all variants.

Split into one chunk per failure scenario. Each gets its own symptom, cause, and fix.
Pattern 04
Terminology Mismatch

The document uses product or UI terminology; users search with task or symptom language. "DRF outbound implementation" doesn't match "data not syncing." The chunk exists; it just doesn't get found.

Add symptom-language synonyms. Lead with how users describe the problem, not what the product calls it.
Pattern 05
Mixed-Intent Chunk

One section covers multiple user intents: how to set something up AND how to troubleshoot it AND when to use an alternative. The chunk retrieves for none of them precisely.

Separate by user intent. Setup, troubleshooting, and reference content should be distinct retrievable units.

Where Audit Questions Come From

The quality of an audit depends on the quality of its questions. Real user questions (not hypothetical ones) reveal the real retrieval gaps.

Best source
Support ticket analytics

ISQM, Zendesk, ServiceNow: closed ticket patterns ranked by volume. Each pattern is a cluster of real user questions. Map subpatterns to derive specific query variants.

High signal
Search query logs

What users typed into the help portal search before opening a ticket or giving up. Zero-result queries are especially valuable; they reveal gaps where no content exists at all.

High signal
AI assistant session logs

Queries that received low-confidence or incorrect AI answers. These are retrieval failures already in production, the highest-priority inputs for any audit.

Supplementary
Task Completion Rate (TCR)

Low-scoring tasks indicate content that doesn't help users succeed, often because the right information isn't retrievable when needed, not because it doesn't exist.

In Practice

The framework applied to SAP APM, using ISQM data as the question source.

Question sourcing

ISQM analysis of 2,753 SAP APM support cases (2023–2026) produced 17 ticket patterns ranked by volume. The top 3 patterns, namely Data Synchronization (319), API Access (296), and Tenant Provisioning (257), became the first audit questions. Subpattern data provided query variants: "S/4HANA equipment not syncing," "X-API-Key request," "BTP subscription failed."

Results

All three questions mapped to existing documentation. All three scored below 5 on the rubric (Not Retrievable). Primary failure modes: Assumed Context (Q1), Cross-Reference Dead End (Q2), and Undifferentiated Errors (Q3). Before/after rewrites produced an estimated retrieval score improvement from 2–3/10 to 8–9/10 for each.
