Methodology · Practice · Philosophy

Documentation that
proves its own value.

User assistance has expanded. Writing is still the core, but the modern UAD measures content effectiveness, uses data to find what's missing, builds tools to work faster, and documents AI in a way that earns user trust. This is how I do it.

The Methodology

Not a one-time project. A continuous loop that turns data into better documentation, and measures whether it worked.

1

Collect data

Pull ticket patterns from ISQM, page performance from Adobe Analytics, task success rates from TCR, self-service behavior from SSR.

2

Identify gaps

Map what customers are struggling with to what documentation exists. Find where the coverage is missing, incomplete, or wrong.

3

Build content

Write or update documentation (help topics, troubleshooting guides, support tree nodes) targeted at the identified gaps, not at what feels important.

4

Measure impact

Track whether ticket volumes drop, task completion rates rise, or search terms shift. Content earns its place by changing behavior, not by existing.

↺  Results feed back into step 1: the loop closes.

The Role Has Changed

Technical writing hasn't been replaced; it's been extended. What a Senior UAD does today vs. what the role used to mean.

Traditional UAD

  • Write documentation from feature specs
  • Follow a set topic structure (context / procedure / result)
  • Measure success by publication dates met
  • React to feedback after release
  • Write for software users (humans doing tasks)

Modern Senior UAD

  • Use analytics data to decide what to write next
  • Design new content formats for new interaction types (AI agents, conversational UI)
  • Measure success by deflection rates and task completion
  • Proactively surface gaps before they become tickets
  • Document AI systems that make decisions, earning trust, not just describing steps

Gap identification & prioritization

Finding a gap is not the same as knowing which one to fix first. I map ticket volumes to documentation coverage, rank by impact, and build a case for where investment will deflect the most tickets.

For SAP APM: 17 ISQM patterns mapped to support tree nodes, ranked by volume, with gap levels and recommended next actions.

AI documentation

AI agents don't behave like software features: they make decisions, use LLMs, and interact with customer data. Documenting them requires a different architecture: scope, responsible AI, data privacy, human oversight.

I developed the 17-section documentation template for SAP APM's AI agents in Joule, now the reference structure for all current and future APM agent docs.

The Business Case

Documentation isn't a cost center if you can measure what it prevents.

2,753 SAP APM support cases analyzed (2023–2026)
94.7% Resolved with no KBA or help portal page used
17 Recurring ticket patterns mapped to documentation gaps
275–550 Estimated tickets deflectable at 10–20% self-service rate

Even a 10% deflection rate on a 2,753-case backlog means 275 fewer support tickets per cycle, fewer cases for DS Dev and Technical Support to resolve, faster time-to-answer for customers, and a measurable return on documentation investment. The data makes the case. The documentation closes the gap.
