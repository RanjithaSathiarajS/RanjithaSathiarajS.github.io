Documentation without measurement is invisible spending

Every enterprise product ships with documentation. Very few teams can tell you whether it is working. The result: writing effort gets directed by instinct, not evidence, and the gaps that actually cost money in support volume stay unfilled quarter after quarter.

What unmeasured documentation looks like

The SAP APM Getting Started Guide topic "Creating a Technical User" was generating 98 SAP for Me visits per period with a self-service rate of 32.65%. That means 66 of those visitors did not find what they needed. Without usage data, that topic looks fine because it exists. With data, it is clearly a high-priority gap.

This pattern repeated across the top 12 topics tracked: documentation existed, but visit volume and conversion data revealed exactly which topics were underperforming and by how much.

What measured documentation looks like

In Q3 2026, SAP for Me visits to APM Help Portal more than doubled: 48 visits in Q2 rose to 106 in Q3, a 121% increase. The self-service rate improved from 31.25% to 36.79%. Ticket count stayed flat at 3 both quarters, despite 2.2 times the volume.

That is a measurable outcome: more users, same tickets, better deflection rate. It happened because content gaps were identified proactively and addressed, not because of luck.

Support tickets are a documentation audit you are already paying for

Every closed support ticket is evidence that a customer could not find the answer in your documentation. That data exists. Most teams never use it to close the gap.

From ticket patterns to deflection targets

Using ISQM (SAP's internal ticket analysis system), recurring failure patterns in SAP APM support tickets were mapped to specific documentation gaps. Three patterns surfaced: missing procedural guidance, no troubleshooting content for known error conditions, and a RAG retrieval failure mode where the answer existed but was not structured for AI-based retrieval.

From this analysis: 297 additional tickets were identified as deflectable through targeted documentation improvements. At an average resolution cost of roughly €21.80 per ticket, that is €6,475 per year. The rewrite scope was 50 to 70 hours of work.

Then the agent was built to accelerate the work

Drafting support tree content for me.sap.com was the most time-intensive step in the deflection workflow. Each node required mapping ticket patterns to decision logic, writing the functional area question, and structuring the content recommendation in SAPROD output format.

A custom Claude Code agent was built, pre-loaded with ISQM patterns, tree node structure, and SAPROD format. The most labor-intensive step in the deflection process was automated. The agent is not a novelty. It is part of the production workflow.

AI features are shipping faster than the documentation architecture exists to support them

Every product team adding Joule agents, RAG pipelines, or AI-assisted workflows needs documentation that earns user trust. That is a different discipline from feature documentation. Most technical writers have not built it yet.

A 17-section architecture built before the template existed

When SAP APM began shipping Joule AI agents, no documentation template existed for agentic features in the APM space. A 17-section architecture was built from scratch, covering: responsible AI disclosures, data privacy, scope and limitations, example prompts, system requirements, output quality guidance, and the trust sections that enterprise AI documentation requires.

This architecture is now the reference for other SAP APM agent docs.

And the documentation quality was tested against AI retrieval

Three real customer questions were run through a RAG simulation using APM documentation. The audit identified three named failure patterns: the Specificity Gap (answers existed but not at the right precision level), the Procedure Scatter problem (steps spread across multiple disconnected topics), and Context Collapse (content that made sense to a human reader failed in a retrieval context because the implicit knowledge was never written down).
